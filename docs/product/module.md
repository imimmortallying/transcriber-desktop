# Продуктовое состояние и направления

Этот документ — source of truth для утверждённых продуктовых решений. Он не
описывает реализацию как существующую, пока её не подтверждает код, и не
заменяет технические документы модулей.

## Текущее состояние

Первая рабочая версия приложения собрана и передана первому внешнему
пользователю для реального тестирования. Локальный pipeline распознавания и
документ расшифровки — рабочая база продукта, а не только внутренний прототип.

Обратная связь от первых пользователей ещё собирается. Поэтому крупные
изменения пользовательского workflow не считаются подтверждёнными
пользовательским тестированием без этой обратной связи. Утверждённый workflow
единого документа не требует такой валидации, но его конкретные детали могут
уточняться по её результатам. Реализованное поведение документа и формат
результатов описаны в [документе расшифровки](../editor/module.md), а запуск распознавания — в
[документе pipeline](../recognition/module.md).

## Утверждённые направления

### Один документ расшифровки

Для пользователя существует один документ — расшифровка записи. Отдельных
экранов Quick и Editor нет. После распознавания текст остаётся в той же области
и с той же геометрией: его можно скопировать, экспортировать в `.txt` или
сразу исправить кликом в текст. Отдельного пользовательского режима
редактирования нет.

Исходная ASR-версия остаётся неизменяемой. Пользовательские правки и список
говорящих хранятся отдельно в существующем проекте прогона; `.txt` — явный
экспорт для человека, не сохранение состояния документа. Правки автоматически
записываются локально после короткой паузы ввода. Перед заменой документа или
закрытием приложения отложенная запись завершается; если она не удалась,
пользователь явно решает, продолжать ли с риском потери последних правок.

Имя говорящего и его текст образуют одну реплику; в рабочем документе имя
нажимается для назначения или смены говорящего конкретной реплики. Управление
самим списком говорящих и вторичные действия скрыты в меню «Ещё» и открываются
поверх стабильной области текста. Среди вторичных действий остаются просмотр
или восстановление исходной ASR-версии и удаление сохранённого прогона с
подтверждением. Старые сохранённые прогоны и проекты правок открываются в том
же документе. История, папка результатов и Client Update относятся к
вторичным действиям меню «Ещё» и открываются в отдельных диалогах с явным
«Назад» или «Закрыть», не сдвигая документ. Автоматическая проверка или
установка обновлений в этот этап не входит.

На старте первым действием остаётся выбор файла. Во время распознавания
показываются только этап pipeline и прошедшее время; процент и движущаяся
полоса не имитируются, пока pipeline не отдаёт достоверный прогресс. Блок
распознавания строго скрыт вне этого состояния. Support Report показывается
только после ошибки в отдельном диалоге; действие открывает папку, где выделен
готовый файл для вложения в письмо.

Интерфейс использует лёгкий локальный UI-kit без внешней зависимости: базовые
отступы, цвета, поверхности, границы, радиусы и тени определены как CSS tokens,
а повторяющиеся блоки используют общие стили. Контекстные подсказки коротко
объясняют следующий шаг и не заменяют действие пользователя диалогом обучения.

### Поставка и обновления

Текущая поставка — Full Offline Setup для Windows. Он устанавливает один
пользовательский продукт, но физически разделяет independently replaceable
Client, тяжёлый ASR Runtime и пользовательские данные. После установки layout
имеет вид `<ASR root>/Clients/<client version>` и `<ASR root>/Runtime`; Runtime не входит в пакет
Client. Полный lifecycle установки, repair и удаления описан в
[документе упаковки](../packaging/module.md).

Каждый публичный Client release выпускается как единый versioned набор: Full
Setup с тем же Client для нового/offline пользователя, а также signed
`.asrupdate`, `latest.json` и `latest.sig` для уже установленного ASR. Новый
пользователь скачивает один Full Setup; существующий пользователь получает
Client-only update внутри приложения. Это release policy, а не combined-update
lifecycle: Full Setup по-прежнему владеет Runtime, launcher, Coordinator,
installer/uninstaller, registry и initial provisioning.

Реализован Client Update: установленный Client выбирает подписанный `.asrupdate`
из локальной файловой системы либо по явному действию проверяет/скачивает
подписанный online release в temporary location. После acquisition оба пути
передают одинаковый локальный package stable Coordinator, который выбирает
Client через `InstallationState`, готовит side-by-side candidate и владеет v2
prepare/activate/READY/commit/rollback. Online check не выполняется при старте
и не является постоянным подключением. Подробные границы, ограничения и
validation evidence — в [Client Update Lifecycle](../client-update/module.md) и
его [матрице](../client-update/validation.md).

Runtime update, Coordinator/launcher self-update и Full Setup handoff в эту
transaction пока не реализованы. Production Client targets the designated
public `imimmortallying/asr-desktop-releases` GitHub Releases endpoint; its
provisioning/publishing remains a release operation. The distribution repository
must contain only public release assets and a minimal README, never source code
or secrets.

Client Update also does not update Windows installer registration, the
uninstaller, bootstrap/Coordinator infrastructure or Runtime. A change to
Installed Apps metadata or any Full Setup-owned component requires a new Full
Setup rather than a `.asrupdate`.

Основная работа ASR остаётся локальной и не должна зависеть от интернета.

### Диагностика и обратная связь

Для поддержки удалённых пользователей реализован локальный Support Report v1:
при критическом сбое приложение или Setup сохраняет минимальный технический
`.txt`-отчёт, который пользователь или посредник вручную отправляет
разработчику. Аудио, видео, тексты расшифровок, проекты и другие потенциально
чувствительные данные не попадают в него и не покидают устройство автоматически.
Точный состав и ограничения — в [документе диагностики](../diagnostics/module.md).
Автоматическая доставка и обратная связь остаются отдельным будущим сервисным
слоем и требуют отдельной trust boundary в [security-документе](../security/module.md).

## Отложенные решения

Монетизация сейчас не проектируется и не реализуется. Архитектура не должна
закрывать путь к будущим моделям — подписке, разовой лицензии, наборам
возможностей или лицензированию организаций. Конкретная модель не выбрана;
сейчас не вводятся auth, payments, subscriptions, licensing или искусственные
тарифы/capabilities. Постоянное подключение к интернету не станет условием
основной работы ASR.
